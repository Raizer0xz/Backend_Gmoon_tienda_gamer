AUTENTICACION EN POSTMAN
------------------------
1. Crea una nueva solicitud POST:
   http://localhost:5050/auth/login

2. En Headers:
   Content-Type: application/json

3. En Body > raw > JSON, reemplaza los datos con una cuenta real:
   {
     "email": "correo@ejemplo.com",
     "password": "tu-password"
   }

4. Pulsa Send.

5. La respuesta devuelve un campo llamado "token", por ejemplo:
   {
     "token": "eyJ...",
     "usuarioId": 12,
     "email": "correo@ejemplo.com",
     "rol": "CLIENTE"
   }

6. Copia solo el valor de "token", sin escribir la palabra Bearer.

7. En las solicitudes protegidas abre Authorization y selecciona:
   Auth Type: Bearer Token
   Token: pega el valor copiado

   Tambien puedes usar la pestana Headers:
   Authorization: Bearer eyJ...

No pongas el JWT en el body ni como parametro de URL.


RENOVACION Y COOKIE EN POSTMAN
------------------------------
El login envia una cookie HttpOnly llamada gmoon_refresh.
Postman debe conservar las cookies del dominio localhost.

Para renovar:
1. Solicitud POST: http://localhost:5050/auth/refresh
2. No agregues Authorization ni body.
3. Enviar sin enviar manualmente el refresh token.

Si Postman no envia la cookie, abre Cookies en la parte superior o
administracion de Cookies y verifica que localhost tenga gmoon_refresh.

La respuesta de refresh contiene un nuevo token de acceso. Debes actualizar
el token Bearer usado en las siguientes solicitudes.

Para cerrar sesion:
POST http://localhost:5050/auth/logout
Sin Authorization. El backend revoca el refresh token y elimina la cookie.


VARIABLES RECOMENDADAS EN POSTMAN
---------------------------------
Crea un Environment con:

base_url = http://localhost:5050
access_token = valor temporal obtenido de /auth/login o /auth/refresh

Usa en las solicitudes:
{{base_url}}/api/v1/productos

Authorization = Bearer {{access_token}}

No compartas el Environment si contiene un token real. No incluyas
passwords ni JWT en capturas de entrega.


ROLES Y PERMISOS ESPERADOS
--------------------------
PUBLICO:
- Login, refresh, logout, registro publico y consulta de productos/categorias.

CLIENTE:
- Crear boletas.
- Consultar solo sus propias boletas.
- Consultar catalogo.
- Abrir /mis-compras en el frontend.

VENDEDOR:
- Consultar catalogo y boletas.
- No crear boletas ni administrar usuarios/catalogo.
- Abrir /vendedor en el frontend.

ADMIN:
- Administrar productos, categorias y usuarios.
- Consultar boletas.
- Crear cuentas CLIENTE y VENDEDOR.
- Abrir /admin en el frontend.

El Gateway vuelve a verificar JWT y rol. Una opcion oculta en el frontend
no reemplaza la autorizacion del servidor.

EJEMPLO BOLETA
--------------
POST {{base_url}}/api/v1/boletas
Authorization: Bearer {{access_token}}
Content-Type: application/json

{
  "clienteNombre": "Cliente Gmoon",
  "email": "cliente@ejemplo.com",
  "tipoComprobante": "BOLETA",
  "items": [
    {
      "id": "42",
      "nombre": "Nombre existente en el catalogo",
      "cantidad": 1,
      "precioUnitario": 1000
    }
  ]
}

El backend vuelve a consultar el catalogo y recalcula precio, stock y total.
El frontend/cliente no debe confiar en el precio enviado.
La compra actual es una simulacion: no cobra ni descuenta stock.


COMPROBACION RAPIDA DE LA AUTORIZACION
--------------------------------------
Sin token:
- Solicitud protegida: debe responder 401.

Token CLIENTE consultando otra boleta/usuario:
- Debe responder 403.

Token VENDEDOR intentando crear boleta:
- Debe responder 403.

Token ADMIN creando/modificando productos:
- Debe responder 200/201 segun la operacion.
